# SDD vs TDD：AI 编程中的分工、协作与边界

> **比较问题**：如何让 AI 理解要做什么，并提供实现符合要求的证据？

## 1. 比较概览

**SDD 明确需求、约束和验收依据；TDD 通过“红—绿—重构”循环，把预期行为转化为可执行测试并驱动实现。** 二者可以组合：规范帮助形成测试，测试为实现提供反馈，但仍需人工确认需求是否合理、验收是否充分。

- **SDD（Spec-Driven Development，规范驱动开发）**：先形成结构化规范（Spec），再据此规划和实现功能。在 AI 编程语境中，其定义与实践方式仍在演化，并无统一的文档格式。[SDD 一手分析](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **TDD（Test-Driven Development，测试驱动开发）**：针对下一项行为先写测试，使其失败，再写足够的实现使其通过，随后重构。先写测试也促使开发者从调用方式和接口出发设计代码。[TDD 定义](https://www.martinfowler.com/bliki/TestDrivenDevelopment.html)

| 比较维度 | SDD | TDD |
|---|---|---|
| 核心问题 | 做什么、边界在哪里、受哪些约束 | 当前行为如何验证、接口如何使用 |
| 主要产物 | 行为规范、验收标准；配套设计和任务计划 | 可执行测试、实现及重构后的代码 |
| 推进方式 | 澄清需求 → 评审规范 → 分解任务 → 实现与反馈 | 失败测试 → 最小实现 → 重构 → 下一行为 |
| 常见粒度 | 功能、变更或跨模块流程 | 单个可验证行为，可涉及不同测试层级 |
| 主要收益 | 显式记录意图与范围，为多次会话提供共同依据 | 缩短反馈周期，支持接口设计与回归检查 |
| 主要成本 | 规范编写、评审和持续维护 | 测试设计、运行和维护 |
| 主要局限 | 规范可能错误、过时或过度细化 | 测试可能遗漏行为，或与实现共享错误假设 |

两者都需要明确当前行为的预期，但无需在开始前穷尽全部需求和设计。TDD 也不是仅适用于函数级测试，更不等同于“代码写完后补测试”。

## 2. 差异本质与共同边界

### 2.1 规范、测试和验收分别约束什么？

```text
业务意图 ──需求讨论与人工评审──→ 规范及验收标准
                                      ↓ 派生与核查
                                  可执行测试
                                      ↓ 驱动与反馈
                                     实现
                                      ↓
                         回归检查、集成验证与人工验收
```

**规范与测试之间的桥梁是验收标准（Acceptance Criteria，AC）**：说明在什么条件下，系统应产生什么可观察结果。业务意图、规范和测试可能同时理解错误，因此“全部测试通过”只能说明被执行的检查通过，不能单独证明功能完整或业务正确。

SDD 常用于功能层，TDD 常用于模块层，但这不是严格边界。规范可以描述模块契约，测试也可以覆盖跨系统流程；选择粒度应依据反馈速度、运行成本与故障定位需求。

### 2.2 规范先行，不等于需求永久冻结

**为当前任务建立足够明确的基线；需求变化时同步修订规范、测试和计划。** 编码前评审与实施中修订是互补环节：前者减少已知歧义，后者吸收新发现。变更应能追溯，不能为了让现有实现通过而悄悄降低验收要求。

Birgitta Böckeler 在 Martin Fowler 网站区分了三种规范使用方式；这是实践分类，并非统一的成熟度标准。[原始分析](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

| 方式 | 规范如何使用 |
|---|---|
| Spec-first：规范优先 | 规范指导当前任务，不必承诺长期维护 |
| Spec-anchored：规范锚定 | 完成后继续维护规范，用于后续演化 |
| Spec-as-source：规范即源 | 人主要编辑规范，代码由工具生成 |

### 2.3 提示约束与执行证据要分开

使用 TDD skill 或写入项目规则，只能提供流程指引，不能单独证明流程得到遵守。应**审查实施计划中的测试步骤，并核对实际运行结果**，确认测试先失败、实现后通过、重构后仍通过。

Hooks 或阶段门控可以在工具调用、代码提交等节点增加检查，但效果取决于实际检查内容：测试文件存在，不代表测试有意义；命令执行结束，也不代表目标断言运行并通过。

## 3. 组合工作流：从规范到交付证据

流程可随任务规模缩减，重点保留明确预期、验证行为和同步变更三个环节。

### 3.1 先形成最小充分规范

规范至少回答四组问题：

1. **目标与范围**：为谁解决什么问题，本次包含和排除哪些功能。
2. **行为与验收**：正常、异常和边界场景下，预期结果是什么。
3. **接口与约束**：数据、权限、输入输出、技术限制；有性能要求时注明负载和测量条件。
4. **改动与依赖**：涉及哪些模块，哪些既有接口必须兼容，还有哪些问题待确认。

例如，“支持密码重置”可细化为“令牌有效期为 15 分钟、仅可使用一次；过期或重复使用时拒绝重置”。其中 15 分钟只是示例参数，实际时限和会话处理策略需业务确认。

**EARS（Easy Approach to Requirements Syntax）** 可用于结构化表达需求，通过条件、触发事件和系统响应等句式减少歧义，例如“当令牌过期时，系统应拒绝密码重置”。句式规范不能替代对业务规则本身的确认。[提出者的说明](https://alistairmavin.com/ears/)

文档可按项目职责拆分为需求、用户流程、技术约束、前后端设计和实施计划，也可按功能组织为 `spec.md / plan.md / tasks.md`。前者便于维护跨功能约定，后者便于追踪单次变更；共同约定宜集中维护，功能规范引用它们，避免重复记录。

### 3.2 按行为执行红—绿—重构

1. **红**：选择一项预期行为，写测试并运行，确认失败原因与目标功能缺失有关。
2. **绿**：实现足够的代码使测试通过，保留断言与运行结果供核查。
3. **重构**：在测试保护下改善结构，并重新运行相关测试。
4. **迭代**：继续下一项行为；新发现的需求或设计决策回写规范。

区分测试失败与测试未能运行：环境、收集或导入错误，不能直接证明预期行为已得到有效测试。路由返回 `404` 是否构成有效失败，取决于测试是否已实际发出请求并检查预期响应；交付前需确认目标断言确实执行。

可用集成或验收测试驱动跨模块子任务，用单元测试验证局部逻辑与边界条件；不必把每条 AC 都转换为端到端测试。测试层级应与行为匹配，避免反馈过慢或重复覆盖。

### 3.3 保存上下文，再检查交付结果

| 机制 | 主要用途 | 使用边界 |
|---|---|---|
| 项目规则文件，如 `AGENTS.md / CLAUDE.md` | 记录跨任务约定与验证方式 | 与具体功能规范分开维护，核对工具是否实际读取 |
| 进度与经验记录 | 保存完成项、下一步、已知问题和纠正结果 | 及时更新，避免把过时记录当事实 |
| Git worktree | 为可分离任务提供独立工作目录 | 仍需协调接口与依赖，合并冲突和集成缺陷仍可能发生 |
| 独立代码评审 | 对照规范、差异及验证证据寻找遗漏 | AI 评审可能共享相同盲点，结论仍需核查 |

交付时，对照 AC 检查实现，运行相关回归与集成验证，并由人确认业务行为和体验。AI 可协助生成规范、测试、实现和评审意见；需求取舍、架构判断及最终验收仍需明确责任人。

## 4. 如何按任务选择投入？

| 场景 | 建议投入 | 原因 |
|---|---|---|
| 新功能、需求边界模糊 | 先澄清规范，再按行为实施 TDD | 先减少对目标的误解，再验证实现 |
| 已明确的缺陷修复 | 简要记录预期行为，先写复现测试 | 用较少文档建立可重复的反馈 |
| 跨模块或多人并行开发 | 明确接口、依赖和改动边界，补充集成检查 | 独立目录无法自动解决语义不一致 |
| 长期维护的核心功能 | 持续维护规范，并保留回归测试 | 使需求变更与代码演化可追溯 |
| 一次性原型、低影响变更 | 使用短规范和必要检查 | 让流程成本与任务复杂度相称 |

评估方法效果时，应同时考虑规范评审、测试维护、集成和返工成本，不能只统计代码生成时间。单个项目的交付天数、测试数量或“零已知 Bug”，均不足以证明通用效率或质量优势。

## 5. 知识网络与来源

### 被比较的方法

- [[规范驱动开发（SDD）]]——以显式规范组织需求、约束和实现任务。
- [[测试驱动开发（TDD）]]——以失败测试驱动实现，并在测试保护下重构。

### 直接相关概念

- **规范与测试的衔接**：[[验收标准（AC）]]将预期行为写成可判定条件；[[EARS]]为需求提供结构化句式，但不能替代业务确认。
- **验证层级与持续反馈**：[[单元测试与集成测试]]帮助选择合适的验证范围；[[回归测试]]检查变更是否破坏已有行为；[[重构]]在保持行为的前提下改善代码结构。
- **规范演化与决策追溯**：[[需求可追溯性]]关联需求、验收标准、测试和实现；[[cs-adr|架构决策记录（ADR）]]保存重要设计选择的背景、理由与后果。
