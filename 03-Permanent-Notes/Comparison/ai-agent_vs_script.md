# Agent 代理执行 vs. 脚本自动化执行（CFD/CSD 及多物理场耦合场景）

> **类型**: 比较笔记
> **比较对象**: [[Agent-based Execution]] vs [[Script-based Automation]]
> **比较维度**: concept / method / code / mixed
> **来源**: 多平台多物理场耦合软件工程实践

---

## 1. 比较概览

### 为什么要比较这两个东西？
在操作 CFD（如 OpenFOAM、ANSYS Fluent、Tranair）、CSD（如 Abaqus、Nastran、Ansys Mechanical）以及它们之间的耦合软件包（如 MpCCI、preCICE、FSI 中间件）时，工程师通常面临两种自动化范式：
1. **脚本自动化**：通过 Shell/Python/Bash 脚本按预设顺序调用求解器、转换数据格式、检查收敛；
2. **Agent 代理执行**：在上层部署具备感知、决策和编排能力的智能体（Agent），由其动态调用底层脚本或命令。

这个比较旨在解决一个架构决策问题：**在复杂、长周期、高失败率的多物理场耦合计算中，是否值得在脚本层之上再引入 Agent 层？**

### 一句话结论
脚本回答 **"How"**（如何精确执行），Agent 回答 **"Whether / When / What-if"**（是否执行、何时执行、出错时如何决策）；二者不是替代关系，而是**分层编排关系**——Agent 通常仍调用脚本，但为其增加了**状态感知、错误诊断、动态策略和人机协同**能力。个人理解，Agent执行就是将”**低级决策**“从人转移到Agent：在script-based下，人来决定一切，人来组织流程，人来完成闭环；但是在agent-based下，整个闭环由agent完成，人只负责顶层设计和高级决策，也就是**Strategic（人）--Tactical（Agent）--Execution（脚本/求解器）**

## 2. 多维度对比表

| 对比维度 | 脚本自动化执行 (Script-based) | Agent 代理执行 (Agent-based) |
|----------|------------------------------|----------------------------|
| **核心定义** | 按预设顺序和条件调用底层命令的确定性程序（Shell/Python/Bash） | 具备环境感知、推理决策和工具调用能力的上层智能体，可动态编排脚本与求解器 |
| **适用前提** | 流程 100% 确定、平台固定、失败模式单一且已知 | 流程存在不确定性、跨平台异构、失败模式多样、需要长周期值守或人机协同 |
| **优势** | 1. 轻量、低 overhead、易于版本控制<br>2. 执行路径透明，可精确复现<br>3. 对 HPC 队列系统（Slurm/PBS）原生友好<br>4. 适合单次确定性任务（如批处理网格生成） | 1. **错误诊断与自愈**：可解析 stderr，识别负体积、发散、 license 不足等，自动重试或回滚<br>2. **动态策略**：根据残差曲线调整耦合松弛因子、切换松/强耦合、动态调整子循环次数<br>3. **跨平台抽象**：统一接口，自动翻译为 `sbatch` / `qsub` / `mpirun`<br>4. **长时状态维护**：维护耦合迭代历史、支持断点续算（从第 47 步恢复）<br>5. **并行编排**：CFD 算第 n 步时，异步预处理第 n+1 步的网格变形与插值<br>6. **人机在环**：在关键节点（残差突跳、网格负体积）主动决策或分级告警 |
| **劣势** | 1. 刚性执行：一旦异常只能 `exit 1`，无上下文恢复能力<br>2. 无状态记忆：每次循环独立，不维护"上一轮为何发散"<br>3. 跨平台脆弱：需为每个平台写 `if-else` 适配<br>4. 人机协作断层：异常时只能停住，无法判断问题严重等级 | 1. 架构复杂度高，引入额外依赖（LLM / 规则引擎 / 向量库）<br>2. 决策过程可能不透明（黑箱），调试困难<br>3. 实时性略低：感知-决策-执行闭环存在延迟<br>4. 对确定性简单任务属于过度设计 |
| **计算成本** | 极低，仅脚本解释器开销 | 中等，Agent 层有推理/匹配开销；但可通过减少人工 babysitting 和无效重算降低**总时间成本** |
| **精度/收敛性** | 依赖人工预设参数，无法在线调整 | 可在线监测残差/力/位移传递误差，动态调整耦合参数，潜在提升收敛鲁棒性 |
| **实现难度** | 低：掌握 Shell/Python + 求解器 CLI 即可 | 中高：需设计感知接口（日志解析器）、决策规则/模型、工具调用 Schema、状态机 |
| **典型应用场景** | 1. 单物理场批量后处理<br>2. 固定参数的风洞算例批跑<br>3. 网格生成→求解→提取升力系数的流水线 | 1. 流固耦合（FSI）长周期迭代值守<br>2. 跨平台（本地→超算→云）异构资源调度<br>3. 优化设计中的自动重网格与重启动<br>4. 多保真度耦合（RANS ↔ LES ↔ CSD）动态切换 |

## 3. 差异本质分析

### 核心差异点
1. **确定性 vs. 动态适应性**
   - 脚本是**开环控制**：输入→执行→输出，执行路径在编码时已冻结。
   - Agent 是**闭环控制**：感知环境（日志、资源状态、残差）→ 推理 → 决策 → 执行 → 再感知。它能在运行时修改执行路径。

2. **状态管理深度**
   - 脚本通过文件/环境变量传递状态，无语义理解（如只知道 `return_code != 0`）。
   - Agent 维护**语义化状态机**（如 "第 12 步耦合因结构大变形导致负雅可比"），并据此做策略级决策（降低位移松弛因子、回滚重算）。

3. **故障处理层级**
   - 脚本处理故障在**语法层**（捕获异常、打印 Traceback）。
   - Agent 处理故障在**语义层**（理解故障根因、匹配历史经验、选择恢复策略）。

### 容易混淆的相似点
- **两者都调用底层命令**：Agent 并不取代脚本，它通常通过 `subprocess` / `pexpect` / API 调用脚本或直接调用求解器 CLI。容易误以为 Agent 是"另一种脚本"。
- **两者都可实现自动化**：脚本也能写 `while` 循环和 `if-else`，形式上具备"简单逻辑"；但缺乏**跨轮次记忆**和**外部知识检索**能力。
- **两者都可在 HPC 上运行**：Agent 本身也可作为作业提交，但它更常作为常驻服务（Daemon）或工作流引擎的插件存在。

### 边界/过渡情况
- **简单耦合流程**：若耦合步数固定、求解器永不发散、平台唯一，脚本完全等价于 Agent，引入 Agent 属于过度工程。
- **Agent 退化为脚本**：当 Agent 的决策规则被写死为 `if error then retry` 且无任何知识库时，它本质上是一个臃肿的脚本。
- **脚本增强版（Workflow Engine）**：如 Airflow、Prefect、Snakemake 等，它们介于两者之间——比脚本多了依赖图和重试机制，但比 Agent 少了语义推理和动态决策。可视为"准 Agent"或 Agent 的底层支撑。

## 4. 决策框架

### 选择指南

| 你的需求/约束 | 推荐选择 | 原因 |
|--------------|----------|------|
| 单物理场、固定网格、固定参数、批量跑 100 个算例 | **脚本** | 轻量、透明、易于版本控制，Agent 无增量价值 |
| 流固耦合/热流耦合，迭代次数未知，求解器可能发散 | **Agent** | 需要动态调整耦合参数、自动重试、断点续算 |
| 需在本地工作站、超算（Slurm）、云（K8s）间无缝迁移 | **Agent** | 脚本需维护多套适配代码；Agent 通过统一抽象层自动翻译资源调度指令 |
| 团队缺乏 Agent 开发经验，且任务周期短（<1 周） | **脚本** | Agent 的学习和架构成本可能超过收益 |
| 需要 7×24 小时无人值守，且失败时需分级告警（钉钉/邮件/短信） | **Agent** | 脚本只能"停住报错"；Agent 可诊断、自愈、告警、甚至自动回滚 |
| 涉及多保真度模型切换（如 RANS 初算 → LES 细算 → CSD 验证） | **Agent** | 需要根据残差/精度指标动态决策何时切换模型，脚本难以表达此类策略 |
| 需与几何参数化、优化算法（如 DOE / 遗传算法）闭环联动 | **Agent + 脚本** | Agent 负责优化策略和异常处理，脚本负责单次求解的确定性执行 |

### 组合使用的可能性
**最佳实践是分层架构，而非二选一：**

```
┌─────────────────────────────────────────────┐
│  Agent Layer (决策、诊断、编排、人机交互)        │  ← 动态策略、错误恢复、资源调度
├─────────────────────────────────────────────┤
│  Workflow Engine (Airflow / Prefect / 自研)   │  ← 依赖图、重试、日志聚合（可选）
├─────────────────────────────────────────────┤
│  Script Layer (Python/Bash/Tcl)               │  ← 求解器调用、格式转换、数据映射
├─────────────────────────────────────────────┤
│  Solver Layer (OpenFOAM / Abaqus / Nastran) │  ← 核心计算
└─────────────────────────────────────────────┘
```

- **Agent 负责"大脑"**：感知日志语义、维护耦合状态、决策是否回滚/降阶/告警。
- **脚本负责"四肢"**：精确执行网格变形、数据插值（如 RBF 映射）、求解器启动、后处理提取。
- **Workflow Engine 负责"神经系统"**（可选）：管理任务依赖、数据流、失败重试的基础能力，为 Agent 提供底层编排支持。
